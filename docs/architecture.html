Feature Pilot · workflow architecture

How one issue becomes a pull request

An autonomous software-engineering agent built on LangGraph: it clones a repository, reads enough of it to plan, edits and tests inside a throwaway container, repairs its own failures, and opens the PR — pausing twice for a human.

Issue URL → Clone → Retrieve → Plan → [approve] → Code → Test → ⟲ Debug → Review → PR summary → [approve] → Fork → Push → Pull request
01

The run, end to end

A run is four things in sequence: pull the issue and the code, stand up an isolated container, drive the agent graph, then publish. Only the third is the agent. The other three are the reason its output can be trusted and its side effects contained.

02

The graph, and the router that is not a model

Eight nodes, one conditional edge each, all pointing at the same function. There is no supervisor vertex, because there is nothing for one to decide: the next node follows from (phase, last typed output). Every node returns a Pydantic contract rather than prose, which is what makes that possible — routing reads tests.success, not a paragraph about how the tests went.

So the supervisor is a pure function. It costs zero tokens, adds zero latency on every transition, and is unit-testable with no model and no container.

Phase is a field, not an inference

Progress lives in one RunPhase enum on the state, with a legal-transition table. Resume reads one field; illegal transitions raise instead of quietly doing the wrong thing. FAILED is reachable from any non-terminal phase and is not listed per row.

03

Retrieval, decomposed so it could be blamed

The retrieve node is four modules behind a Retriever protocol, each benchmarked on its own against ground truth from real bugfix commits. That split is what let the measurement land somewhere specific instead of on “retrieval”.

04

Where the agent's hands are

Nodes never import LangChain or MCP types. They ask a ToolRegistry, which is populated by discovery over MCP at run start — so a test can hand a node fakes with no MCP process anywhere. Every tool ultimately lands inside one container that is destroyed with the run.

05

Driving and watching a run

The graph emits one MetricEvent per node boundary, tool call, model call and phase change. A composite sink fans those out: Postgres for the durable log and its projections, Redis for the per-run channel the SSE endpoint subscribes to, and .fp/runs/<id>/ for bulk artifacts — the diff, the test output, the context that was actually sent.

endpointdoes
POST /runsStart a run from an issue URL. Reserves a concurrency slot; 201 with the run id.
GET /runs/{id}Current phase, spend, and the pending interrupt payload if the graph is parked.
GET /runs/{id}/streamSSE over the run's Redis channel — every event, replayed from the start.
POST /runs/{id}/approveAnswers the interrupt with a HumanDecision; the graph resumes from its checkpoint.
GET /runs/{id}/artifactsThe diff, the test output, the retrieved context, the PR summary.
POST /runs/{id}/publishGate ②. Branch → patch → commit → fork → force-push → PR. Idempotent per issue.
DELETE /runs/{id}Cancel; the sandbox is destroyed and the slot returned on every exit path.
06

The seams that make it measurable

Two config-level axes exist so that “the agent” is never one indivisible thing. Stages can be switched off to ask what each one contributes; roles map to models so re-tiering for cost is one edit rather than a hunt through node modules.

Cumulative token budgets are kept only as a runaway backstop: in a tool loop the same context is re-sent every turn, so one piece of information is billed once per iteration and the ceiling measures the transcript rather than the work. Cost is the honest instrument. A BudgetExceeded is terminal by definition — a retry would exceed it too.
